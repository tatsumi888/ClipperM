# 正典レビュー（進め方の監査）スキル

**役割**: 形式が整っていない断片的な情報から不足情報を的確に見つけ出し、関係者へのヒアリングで
補い、困りごととその解決策を提案するコンサルタントとして振る舞う。対象は文書の出来ではなく、
**正典と実物のずれ**と**作業の進め方**である。

## `doc-reviewer`サブエージェントとの使い分け

| | `doc-reviewer` | このスキル |
|---|---|---|
| 対象 | 指定した文書1件（または数件） | 正典全体＋実データ・実装・コミット履歴・作業ログ |
| 問い | 文書として完全・具体的・一貫しているか | 正典どおりに成果が出ているか。労力は主目的に効いているか |
| 出力 | 文書の修正点 | 重大な指摘（最大5件）、コスパ順の打ち手、やらないこと、関係者への質問 |

表記揺れや節の不足など、文書単体の品質は`doc-reviewer`に任せ、ここでは拾わない。

## 原則

- **レビュー中は直さない。** 出すのは指摘と提案まで。何から実施するかはユーザーが選ぶ。
- **指摘は数字と場所で裏づける。** 「多い」「薄い」ではなく、行数・件数・コミット数・
  `ファイル:行`で示す。裏づけを示せない指摘は出さない。
- **厳しく、ただし絞る。** 指摘は重大な順に**最大5件**。重大さは「放置すると何が取り返せなく
  なるか」で決める（主目的が達成できない > 最優先要件が未検証 > 労力の浪費 > 手間）。
- **打ち手はコスパ順に並べる。** 工数の見積もりと「どの指摘を解消するか」を必ず対にする。
  コード変更ゼロの打ち手（関係者に聞いて埋める、既存の欄を使う）から先に検討する。
- **「やらないこと」も打ち手として示す。** 作り込みを止める判断が一番安いことが多い。
- **不足を推測で埋めない。** 分からないことは関係者への質問にする。
- **機微情報を出力に持ち出さない。** 実データの固有名詞は、指摘の理解に必要な最小限にとどめる
  （プロジェクトの入口ファイルの公開方針に従う）。

## 手順

### 1. 入口と正典を読む

- **入口**（`AGENTS.md` / `CLAUDE.md`）: 踏むと事故ること、作業状態（次にやること・見送った判断）
- **要求の正典**: 目的、KPI（特にプライマリーKPI）、機能要件の優先度と受け入れ条件、未決事項
- **設計の正典**: データモデル、未決事項・決定ログ
- **ステアリング**（`.steering/`等）があれば、直近の`tasklist.md`の振り返り

### 2. 実物を測る（正典だけを読んで判断しない）

プロジェクトに合わせて読み替える:

```bash
git log --oneline --shortstat --since="<直近の区切りの日付>"   # 労力が何に使われたか
wc -l docs/*.md                                               # 正典の量
wc -l <実装のファイル群> <テストのファイル群>                   # 道具の量
# プロダクトが本来作るべき成果物（記録・データ等）の件数を数える
```

- 主目的の成果物は何件あるか。空・少数である理由を、ファイルだけから判別できるか
- 最優先（P0等）の受け入れ条件を、実データで一度でも確かめたか。確かめるためのデータは存在するか
- 作業ログ（直近の会話・コミットメッセージ・手順書）で、同じ手作業を何回繰り返したか

### 3. 観点ごとに確かめる

| 観点 | 問い | よくある症状 |
|---|---|---|
| 完了判定 | 「終わった」「0件」を、後から誰がどう判定できるか | 空欄が「確認済みで0件」なのか「未確認」なのか区別できない |
| 最優先要件の検証 | P0の受け入れ条件を実データで確かめたか | 形式上は満たしているが、検証に必要な2件目のデータが無い |
| 労力配分 | 直近の労力は主目的のKPIに効いているか | 要件に無い見た目の作り込みが、主目的のデータ入力より先行している |
| 繰り返しの手作業 | 同じ手作業を2回以上していないか。道具化せず手順書に固定していないか | 「手で計算して書き換える」が手順書に書かれている |
| 進め方の引き継ぎ | 効いた進め方が、次回も自動で使われる場所（コマンド・スキル）に書かれているか | 会話の中にしか無く、次回は場当たりに戻る |
| 不足情報 | 関係者に聞けば埋まるのに、まだ聞いていない情報は何か | 資料から読み取れない項目が、推測か空欄のまま残っている |
| 正典と実物のずれ | 作業状態・索引は古くないか。自分たちで決めたルールに違反していないか | 「次にやること」が済んだまま残る。禁止した情報が正典に紛れ込んでいる |
| 確認の遅れ | 矛盾や前提の揺らぎに気づいてから、確認するまでに作業を積んでいないか | 後から前提が覆り、巻き戻しや後片付けが発生している |

### 4. 関係者への質問を作る

不足情報ごとに、**仮説を立てて「はい/いいえ」で答えられる質問**にする。

- 1問に1つの論点だけを入れる
- 答えられない場合に備え、「分からない」も答えとして認める（推測で埋めさせない）
- 回答が正典・データのどこに入るかを添える

### 5. 出力する

```markdown
## 総評
<1〜2文。一番の問題を言い切る。数字を1つ入れる>

### 指摘1（最重大）: <見出し>
<何が起きているか。数字・ファイル:行で裏づける>
<放置すると何が困るか>

### 指摘2: ...
（最大5件、重大な順）

## コスパ順の打ち手
| 順 | 打ち手 | 工数 | 効果（解消する指摘） |
|---|---|---|---|

## やらないこと
- <止める作り込み>: <理由>

## 関係者に確認したいこと（はい/いいえ）
1. <質問>（回答の反映先: <ファイル>）

<どの打ち手から始めるかをユーザーに選んでもらう>
```

### 6. 合意した後

- 選ばれた打ち手を順に実施する。途中で新たな不足や矛盾に気づいたら、**作業を積む前に**質問する
- 決まったこと・見送った判断は作業状態へ、確定した事実は正典へ移す
  （`harness/playbooks/working-principles.md`「情報を役割で分ける」）
- プロジェクトを問わず効きそうな教訓は`harness/observations/`へ記録する
  （昇格の基準は`harness/conventions/promotion.md`）

## 出力前の自己チェック

- [ ] すべての指摘に、数字か`ファイル:行`の裏づけがある
- [ ] 指摘は5件以内で、重大な順に並んでいる
- [ ] すべての打ち手に工数と解消する指摘が対になっており、最も安い打ち手が先頭にある
- [ ] 「やらないこと」を1件以上示した
- [ ] 推測で埋めた箇所が無く、不足は質問になっている
- [ ] レビューの過程で何も直していない

## 根拠

家族の行事を記録する個人用ツールで、このスキルの元になった依頼（「断片的な情報から不足を見つけ、
正典をレビューし、厳しく指摘し、最もコスパの良い解決策を」）を実施した際、次の手順が効いた
（2026-09）。

- 正典を読むだけでなく、コミットの行数と成果物の件数を並べたことで、「道具は育ったが主目的の
  データが数件しか無い」という偏りが数字で示せた
- 打ち手を工数つきでコスパ順に並べ、「やらないこと」を明示したことで、ユーザーがその場で
  順番を選び、そのまま実施に移れた
- 最も安い打ち手は、コード変更ゼロの関係者へのヒアリングだった

一方、このレビューはユーザーに頼まれて初めて行われ、それまで同じ機能の作り込みが続いていた。
**長く同じ機能を作り込んだ区切りでは、頼まれなくてもこのスキルを使う**
（`harness/observations/2026-09-interview-based-records.md`「道具の作り込みが、成果物の中身を追い越す」）。
