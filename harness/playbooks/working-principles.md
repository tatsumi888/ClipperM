# 進め方の方針

プロジェクトを問わず適用する、作業の進め方の方針。**この内容の正典は本ファイルである。**
各プロジェクトのルート直下の `AGENTS.md` / `CLAUDE.md` からはここを指し、**内容を書き写さない**
(書き写すと必ず片方が古くなる)。

## 言語

ユーザーへの応答・ドキュメント(`docs/`、`.steering/`)はすべて日本語で記述する。コード内の
識別子のみ英語とし、コメント・コミットメッセージも日本語で書く。仕様書が日本語で書かれている
ため、混在させない。

## 情報を役割で分ける

**根拠**: あるプロジェクトで長期の調査・修正を続けた結果、判断の理由も残件も会話の中にしか
存在せず、再開のたびに同じ検討をやり直す状態になった。以下はそこで実際に効いた対処を
一般化したものである。ファイル名や構成は各プロジェクトの流儀に合わせてよいが、**役割は欠かさない**。

| 役割 | 置くもの | 無いと起きること |
|---|---|---|
| **入口** | プロジェクトの概要、資料の索引と読む順序、踏むと事故ること | どこから読めばよいか分からず、重要な制約を踏む |
| **作業状態** | 未対応の残件、未確認の事実、**見送った判断とその理由** | 会話が終わると失われ、再開のたびに同じ検討をやり直す |
| **正典** | 確定した仕様・設計・用語・調査結果 | 確定と未確定が混ざり、どれを信じてよいか分からなくなる |
| **利用者向け** | 使い方、判断が必要な場面の選び方 | 開発者しか使えないものになる |

**入口から作業状態へ1ホップで届くようにする。** 導線が1か所しかないと、そこに辿り着くこと自体が
偶然頼みになる。Claude Code が自動で読むファイル(`CLAUDE.md`)と、人間が最初に見るファイル
(`README.md`)の**両方から**指す。

## 作業状態の書き方

- 各項目に**根拠**と**次に何をすれば進むか**を書く。根拠のない「気になる」は書かない
- 片付いたら**その項目を消す**。判明した事実は正典へ移す
- **「見送った判断」を理由つきで残す。** これが無いと、既に検討して却下した案を次の担当者
  (や将来の自分)が再提案する
- 「利用者の操作で解決すること」と「実装しないと残ること」を分ける

## 確定した事実は正典へ移し、根拠を添える

用語集や設計書は、名前の説明にとどめない。**実物を調べて初めて分かった事実を、どのデータで
どう確かめたかとともに記録する。** これが無いと、次に同じ現象を見たときに自分たちの不具合として
直そうとする。

## 症状から原因を推測せず、実物で再現してから断定する

外部から取り込んだデータが絡む不具合では、原因が自分たちの側にあるとは限らない。

- 実データやサンプルで**まず再現する**
- 再現したら、**期待値を手計算で出して**どちらが正しいかを確定させる
- 直す前に「これは本当にこちらの誤りか」を疑う

推測で直すと、正しい実装を壊すことになる。

## 二重管理を作らない

同じ内容を2か所に書くと、必ず片方が古くなる。ドキュメントを画面にも出す場合は、**原本を
唯一の情報源として読み込む**(書き起こしをしない)。データやプリセットを複数箇所に持つ場合は、
**食い違いを検出するテスト**を置く。

## マージはユーザーの明示的な指示を待つ

ブランチを切り、そのプロジェクトの検証コマンドを通すところまでは進めてよい。**`main` への
マージは指示があるまでしない。** 検証が通ったことと、利用者が結果を受け入れたことは別である。

## 破壊的な操作の前に退避を促す

手入力・手作業で作ったデータは、取り込み直しや再生成では復元できないことが多い。削除・リセット・
上書きを提案するときは、**先にバックアップを促し、何が復元できて何ができないかを明示する**。
